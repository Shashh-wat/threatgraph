ThreatGraph

A Neo4j-powered GraphRAG engine that stores threat actors, CVEs, software, and intelligence reports as one connected graph, and answers multi-hop security questions by combining vector search with Cypher traversal.

Neo4j 5.24 · property graph Native vector index Streamlit UI Working build, verified end-to-end
01

The problem

Security teams track three things that are really one question apart: which CVEs exist, which threat actors exploit them, and which software those CVEs affect. Today those live in three disconnected places — CVE databases, vendor actor-attribution reports, and free-text advisories.

Asking “which threat actors target our database systems, and how do we mitigate that” means manually cross-referencing all three by hand. A relational join can connect the structured records, but can’t reason over the unstructured mitigation text inside an advisory — and a keyword or vector search over the advisories can’t recover the structured actor→CVE→software chain.

02

Objectives

  • 01Model actors, vulnerabilities, software, and reports as a single connected property graph in Neo4j.
  • 02Store vector embeddings of report and CVE text as node properties, exposed through Neo4j’s native vector index.
  • 03Build hybrid retrieval — vector similarity plus multi-hop Cypher traversal — instead of vector search alone.
  • 04Use an LLM to synthesise an answer grounded only in the graph context actually retrieved.
  • 05Ship a Streamlit UI showing the answer, the Cypher that ran, and the nodes retrieved — the reasoning is inspectable, not a black box.
03

Why a graph, not tables

The core data here is relationships, and the number of hops needed isn’t fixed in advance — “what else does this actor target” is a variable-depth walk, not a fixed join.

Relational schema

EXPLOITS and AFFECTS become junction tables. “Everything connected within N hops” needs a recursive CTE that gets slower and harder to write as N grows. A new relationship type (e.g. TARGETS → sector) means a migration.

Neo4j property graph

Each relationship is a stored, directly-traversable pointer — walking actor → CVE → software is a constant-time hop, not a join whose cost grows with table size. The schema absorbs a new relationship type with no migration.

A document store (e.g. MongoDB) was also considered, but it forces a choice between duplicating actor/CVE data into every report (embedding) or resolving reference IDs in application code for every multi-hop question (referencing). Neo4j avoids that trade-off outright — relationships are native, not simulated.

04

Data model

A property graph: labelled nodes with key-value properties, connected by typed, directed relationships. Conceptually many-to-many at every step — one CVE is exploited by several actors, one actor typically exploits several CVEs.

The eight queries

Queries 1–2 are the two pipeline stages above, run standalone; 3–5 are the project-specific retrieval/aggregation queries; 6–8 demonstrate create, update, and delete.

#PurposeCypher
1Vector search for relevant reports/CVEsdb.index.vector.queryNodes(...)
2Multi-hop expansion from a seed nodeMATCH (seed)-[*1..2]-(connected)
3Actors exploiting CVEs that affect database software(a)-[:EXPLOITS]->(v)-[:AFFECTS]->(s)
4Reports describing a given actor's CVEs(a)-[:EXPLOITS]->(v)<-[:DESCRIBES]-(r)
5Rank software by number of targeting actorscount(DISTINCT a) ORDER BY ... DESC
6Create — add a newly disclosed CVEMERGE (v:Vulnerability:CVE {id: $id})
7Update — revise a CVE's severitySET v.severity = $new_severity
8Delete — remove a retracted reportDETACH DELETE r
 
// Query 5 — full text, as run against the live database
MATCH (a:ThreatActor)-[:EXPLOITS]->(:Vulnerability)-[:AFFECTS]->(s:Software)
RETURN s.name AS software, count(DISTINCT a) AS actor_count
ORDER BY actor_count DESC
